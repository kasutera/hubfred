# Cache Strategy

This document describes the current cache behavior and recommended direction. The recommendations are not current behavior.

## Current behavior

- The `pr` and `is` pickers use Alfred's cache with a 30-second lifetime and loose reload. They have no credential-specific cache key; after switching GitHub CLI accounts, run `reload` in Alfred.
- On dashboard launch, Alfred first preloads any cached list, then starts an asynchronous refresh. `prs` and `iss` have separate JSON files (`dashboard-v2.json` and `issues-dashboard-v2.json`); each stores the combined results, including descriptions (`body`), in the same entry as its list item. A matching cache younger than 30 seconds skips the request. From 30 seconds to under 10 minutes, the matching old list stays visible during refresh; a failed refresh with the same resolved identity leaves that data intact. If authentication cannot be resolved or changes during refresh, the loader clears the displayed rows and detail preview, shows the existing failure placeholder, and neither displays nor caches the fetched results. Without a matching cache, or once it is 10 minutes old, the dashboard tries to refresh without showing old data; if that request fails, it displays a failure placeholder. Ten minutes is the display-freshness window, not a deletion deadline.
- The preview reads an item's description from the matching dashboard cache by URL. It does not fetch the body or check a separate preview expiration time.
- Dashboard cache identity is a SHA-256 digest of the effective github.com token: the first nonempty `GH_TOKEN`, then nonempty `GITHUB_TOKEN`, otherwise the output of local `gh auth token --hostname github.com` using the search command's PATH and environment settings. The CLI lookup is local (no network) and its stderr is suppressed. If no token is resolved, dashboards do not read or write the cache; refresh shows the existing failure placeholder and preview is unavailable. Only the digest is stored; the raw token is passed to `search.sh` only as its `GH_TOKEN` environment value, never as an argument, log, or file. Changes to a Keychain-backed `gh` login are reflected when the CLI resolves the new token.
- The default cache directory is Alfred's `$alfred_workflow_cache`, or `$HOME/Library/Caches/jp.kasutera.hubfred` when that variable is unset. Dashboard results, including descriptions, are persistent plaintext JSON. The dashboard loader uses `umask 077`, so a newly created cache directory and its temporary cache files are owner-only; it does not change permissions on an existing directory. Updates write a temporary file and replace the cache file atomically, but there is no lock or single-flight coordination: overlapping refreshes can race, and the last successful replacement wins.
- Generated Octicons are stored under the versioned `octicons-v5` directory in the same cache root. The 64px PNGs use 87.5% glyph scaling; six muted repository colors and distinct issue, ready-PR, and draft-PR shapes make the icons deterministic and independent of account credentials. The glyphs come from [Octicons v19.19.0](https://github.com/primer/octicons/tree/v19.19.0/icons).
- The screenshot workflow has a separate Bundle ID and cache at `$HOME/Library/Caches/org.hubfred.screenshots`. It uses synthetic fixtures and does not connect to GitHub CLI, keeping demo data and generated icons separate from production.

## Recommended direction (not current behavior)

- Coalesce concurrent refreshes by `(verified identity, dashboard kind)` so launches for the same account and `prs` or `iss` share one update; keep the two kinds independent.
- Fetch descriptions only when an item is selected and do not persist their bodies. This avoids retaining full descriptions in the dashboard cache, at the cost of an extra request and preview latency; the preview should communicate loading and handle request failures.
